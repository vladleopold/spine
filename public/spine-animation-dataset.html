Why it exists

From raw animation exports to LLM-ready records.

Our company has spent years collecting, normalizing, and cataloging production Spine animation sources: JSON/SKEL skeletons, atlas files, texture pages, animation names, runtime states, and usage metadata.

The dataset is designed for technology companies training or evaluating agents that understand animation structure, generate valid Spine-ready JSON, write JavaScript playback logic, and reason about asset roles across commercial domains.

Schema-first corpus

A catalog built for supervised data, retrieval, and evaluation.

Every asset package is transformed into a structured record with domain, asset category, animation type, skeleton type, content type, taxonomy, tags, file specs, source paths, and inference confidence. 

{
  "domain": "gamedev",
  "asset_category": "ui",
  "animation_type": "ui",
  "skeleton_type": "ui",
  "content_type": "ui",
  "taxonomy": {
    "category": "ui",
    "class": "interface",

    "tags": ["panel"]
  },
  "tags": {
    "gameplay_role": ["interface"],
    "animation_state": ["idle", "win", "open"],
    "rig_type": ["spine-json"],
    "resolution": ["texture-png"]
  }

For agents that need to create animation, not only describe it.

Internal systems

Prepared with an automation stack for animation data.

Production-ready Auto-tagging Pipeline for classifying source animation packages into commercial asset categories.

GSD

Generator of Synthetic Dataset variants for expanding instruction, schema, and evaluation coverage.

PFAPP

Python FastAPI plus Python Pipeline for ingestion, validation, transformation, and private catalog operations.

SLR
