# Repository layout and data lifecycle

## Canonical ownership of files

- Application code belongs in `src/`, `api/`, and `lib/`.
- Executable maintenance and conversion utilities belong in `scripts/`.
- Automated tests belong in `tests/`; reusable test fixtures belong in a clearly named fixture directory under `tests/`.
- Browser-served static content belongs in `public/` or the explicitly maintained `assets/` tree.
- The active upload collection is `library/`. Numbered collections (`library_01/`, `library_02/`, and later shards) are durable historical storage.
- Structured model metadata, taxonomy, and catalog indexes belong in `data-science/`.
- Build output belongs in `dist/` and is generated by Vite. It is not source.
- Temporary diagnostics and screenshots belong in `diagnostics/`, not beside application source.

## Why project directories still exist at the repository root

Root-level timestamped project directories are legacy published data, not source-code modules. They may be referenced by records in `data-science/items/`, old manifests, source-proof documents, blockchain-anchor documents, or already published `/assets/...` URLs.

They are intentionally not moved by this cleanup. A safe migration must:

1. Enumerate every index, manifest, proof, anchor, sitemap, and runtime reference to the old path.
2. Copy the full project tree without changing file bytes.
3. Verify SHA-256 and byte lengths for every source file and proof document.
4. Update all path-bearing records in a single reviewed migration.
5. Preserve old public paths through explicit compatibility rewrites or immutable aliases.
6. Verify representative old and new URLs and compare proof hashes before retiring any old path.

Until all six steps are complete, the original directory is the authoritative compatibility copy.

## Upload destination invariant

New uploads must use exactly one project directory under the active library collection or a numbered collection, for example:

- `library/<project-id>/`
- `library_01/<project-id>/`
- `library_02/<project-id>/`

The API validates this before writing any project file. Root-level upload destinations, path traversal, nested arbitrary destinations, and similarly named non-collection directories are rejected. Existing legacy root-level projects remain readable and are not rewritten by this guard.

The `library/index.json` and collection indexes remain the source of truth for public discovery. Do not create a second manually maintained project index.

## Deployment behavior

Vercel serves the repository root as the project root, builds with `npm run build`, and publishes `dist/`. Existing API rewrites and asset routes are part of the public contract. Moving a file that is named in `vercel.json`, a sitemap, or a generated public URL requires an explicit compatibility change.

## Root directory policy

Keep the root limited to project configuration, deployment metadata, concise project documentation, and files that must be served from a stable root URL (for example robots and sitemap files). Do not add new timestamped project folders, screenshots, local exports, or temporary parser outputs at the root.

Before adding a new root-level file, determine whether it is:
- required by the toolchain or deployment platform;
- a stable public URL with a documented compatibility requirement; or
- better placed under `docs/`, `diagnostics/`, `scripts/`, `assets/`, or the library data tree.

This policy is enforced for new upload writes by the API guard. Historical content is migrated separately and conservatively.
